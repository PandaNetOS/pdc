# ADR-001: 架构边界与分层原则

> 状态：✅ 已采纳
> 日期：2026-09-08
> 决策者：项目维护者
> 相关：架构重构、数据层统一

## 背景 (Context)

PDC 项目在快速迭代过程中，出现了以下架构问题：

1. **职责边界模糊**：数据层（Repo）、业务层（Services）、智能层（Intelligence）之间的职责划分不清晰，存在越权操作
2. **数据分散**：同一份数据（如 DHT 节点）被存储在多个地方（路由表、NodeRepo、JSON 文件），造成数据不一致和重复持久化
3. **智能逻辑分散**：评分计算、冷热判断、节点选择等智能逻辑分散在各个模块中，难以统一维护和优化
4. **性能问题**：由于职责不清，出现了频繁的全量克隆、重复持久化等性能问题（如每次 DHT 响应后全量保存 60000+ 节点，导致 10 MB/s 持续磁盘 IO）

## 决策 (Decision)

采用**四层架构**，明确各层职责边界：

```
┌─────────────────────────────────────────┐
│  接入层 (Entry)                          │
│  HTTP REST / WebSocket / UDP / TCP / DHT│
├─────────────────────────────────────────┤
│  业务服务层 (Services)                    │
│  Discover / Crawler / Tracker / Probe... │
│  ✋ 只负责业务逻辑，不做智能决策          │
├─────────────────────────────────────────┤
│  智能层 (Intelligence)                    │
│  ScoreSystem / TierSystem / SelectSystem │
│  ✅ 唯一的智能决策入口                    │
├─────────────────────────────────────────┤
│  数据层 (Repositories)                    │
│  NodeRepo / PeerRepo / TrackerRepo / ... │
│  ✋ 只负责数据存储和查询，不做智能判断    │
├─────────────────────────────────────────┤
│  存储层 (Storage)                         │
│  内存缓存 (parking_lot::RwLock)          │
│  SQLite (WAL 模式)                        │
└─────────────────────────────────────────┘
```

### 核心原则

1. **智能层统一收口**：所有智能决策（评分、冷热、选择）统一在 intelligence 层
2. **数据层唯一真相源**：四大 Repo 是所有关键数据的唯一归口，业务模块通过 trait 访问
3. **业务层不越权**：业务服务只负责业务逻辑，不直接操作底层存储，不自行计算评分
4. **增量优先**：评分重算、数据持久化等操作优先采用增量方式
5. **可观测性**：关键操作都有统计和日志

### 具体约束

- ❌ 禁止业务层直接调用 `repo.update_score()`，必须通过 ScoreSystem
- ❌ 禁止 Repo 层做冷热判断，必须通过 TierSystem
- ❌ 禁止业务层自行实现节点选择，必须通过 SelectSystem
- ❌ 禁止同一份数据存储在多个地方
- ✅ 所有产生的来源数据必须全部存入对应 Repo

## 后果 (Consequences)

### 正面影响
- **职责清晰**：每层职责明确，代码更易理解和维护
- **性能提升**：消除了重复持久化、全量克隆等性能问题（磁盘 IO 从 10 MB/s 降到 < 1 MB/s）
- **可扩展性**：新增智能逻辑只需在 intelligence 层添加，不影响其他层
- **可测试性**：各层可以独立测试，通过 trait mock 依赖
- **数据一致性**：唯一真相源，避免数据不一致

### 负面影响 / 代价
- **重构成本**：需要重构现有代码，调整模块依赖关系
- **学习成本**：新开发者需要理解四层架构和职责边界
- **间接调用**：业务层需要通过智能层间接访问数据，调用链变长

### 风险
- **过度设计**：如果项目规模不大，四层架构可能过于复杂
- **性能开销**：trait 对象的动态分发可能有微小的性能开销（可忽略）

### 缓解措施
- **渐进式重构**：不一次性重构所有代码，按模块逐步迁移
- **文档完善**：通过架构文档和 ADR 记录设计决策，降低学习成本
- **性能验证**：重构前后进行性能对比，确保没有性能回退

## 替代方案 (Alternatives)

### 方案 A：三层架构（接入/业务/数据）
- 优点：更简单，层数少
- 缺点：智能逻辑分散在业务层和数据层，难以统一维护
- 不选择的原因：智能逻辑（评分/冷热/选择）越来越复杂，需要独立成层

### 方案 B：微服务架构（每个模块独立进程）
- 优点：独立部署，独立扩展
- 缺点：运维复杂，进程间通信开销大，不适合当前项目规模
- 不选择的原因：PDC 是单进程 Agent，微服务架构过重

### 方案 C：保持现状（不做架构分层）
- 优点：无需重构，短期成本低
- 缺点：技术债务累积，性能问题难以解决，代码难以维护
- 不选择的原因：已经出现了严重的性能问题（10 MB/s 磁盘 IO），必须重构

## 实施计划 (Implementation Plan)

- [x] 建立四层架构骨架
- [x] 四大 Repo 统一归口（Node/Peer/Tracker/Infohash）
- [x] 智能层统一收口（ScoreSystem/TierSystem/SelectSystem）
- [x] 移除重复持久化（JSON 文件、路由表 SQLite）
- [x] 移除 crawler 中的即时全量保存
- [x] 性能验证（磁盘 IO 从 10 MB/s 降到 < 1 MB/s）
- [ ] 完善架构文档
- [ ] 完善 ADR 记录

## 验证标准 (Verification Criteria)

- [x] 所有业务模块通过 Repo trait 访问数据，无旁路
- [x] 所有智能决策通过 intelligence 层，无分散逻辑
- [x] 同一份数据只存储在一个 Repo 中
- [x] 磁盘 IO < 1 MB/s（持续运行时）
- [x] 127 个单元测试全部通过
- [x] PDC 启动后正常运行，监控窗口可连接
