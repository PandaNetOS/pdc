# ADR-002: 智能层统一收口（评分/冷热/选择）

> 状态：✅ 已采纳
> 日期：2026-09-08
> 决策者：项目维护者
> 相关：评分系统、冷热分层、节点选择

## 背景 (Context)

在架构分层（ADR-001）的基础上，智能层（Intelligence）的职责边界需要进一步明确。之前存在以下问题：

1. **评分逻辑分散**：
   - NodeScorer、PeerScorer、TrackerScorer 各自独立
   - ScoreMaintainer 每 60 秒全量重算所有节点评分
   - 各个模块可能直接调用 `repo.update_score()`，绕过评分系统
   - 新发现的节点要等 60 秒才能有评分

2. **冷热判断分散**：
   - NodeRepo 的 `save_all()` 自己做冷热过滤（只保存最近 2 小时活跃的节点）
   - PeerRepo 的 `save_all()` 也自己做冷热过滤
   - TierManager 只做统计，不实际控制持久化
   - 冷热判断的依据单一（只看最后活跃时间），不考虑评分和访问频率

3. **节点选择分散**：
   - crawler/engine.rs 自己实现 `select_diverse_nodes()`
   - 每次选择都全量克隆 60000+ 节点
   - 其他模块可能有自己的选择逻辑

4. **性能问题**：
   - 评分全量重算：60000 节点逐个更新，60000 次锁竞争 + 60000 次 SQLite UPDATE
   - 节点选择：每次全量克隆 60000+ 节点，大量内存分配
   - 健康度计算：每次全量克隆所有节点

## 决策 (Decision)

智能层统一收口所有智能决策，建立三大子系统：

### 1. ScoreSystem（评分系统）

**增量评分 + 脏标记 + 批量更新**：

```
统计更新 → mark_dirty(addr) → 每10秒增量重算脏节点 → update_scores_batch()
```

- **脏标记**：节点统计数据更新时自动标记为脏
- **增量重算**：每 10 秒只重算脏节点（通常 < 1000 个）
- **全量兜底**：每 300 秒全量重算一次，确保一致性
- **批量更新**：一次事务更新所有评分，避免 60000 次锁竞争

### 2. TierSystem（冷热分层系统）

**多维度判定 + 统一接口**：

| 维度 | 权重 | 说明 |
|---|---|---|
| 最后活跃时间 | 40% | 最近活跃的更可能被再次访问 |
| 节点评分 | 30% | 高评分节点更可能被爬虫选择 |
| 访问频率 | 20% | query_count 高的节点更活跃 |
| 数据重要性 | 10% | 预留扩展 |

**特殊规则**：
- 高评分保底：评分 > 70 的节点，即使暂时不活跃也至少保留为温数据
- 低评分加速降级：评分 < 30 的节点，热阈值缩短为 1/3
- 访问频率调整：高频访问热阈值延长，低频访问加速降级

**统一接口**：
- `classify_node(last_active, score, query_count) -> DataTier`
- `should_persist(...) -> bool`
- `should_keep_in_memory(...) -> bool`

### 3. SelectSystem（节点选择系统）

**统一选择接口 + 性能优化**：

- `select_diverse_nodes(repo, count, max_per_subnet)` — 多样性选择（爬虫用）
- `select_top_nodes(repo, n)` — 按评分选 Top N
- `select_crawl_candidates(repo, count, max_per_subnet)` — 爬虫候选选择

**性能优化**：
- 只取 Top 500 候选池（非全量 60000）
- 遍历引用不克隆，只在最后返回时克隆
- 内存分配从 60000+ → 500

### 4. HealthScorer 优化

- 改用 `stats()` 替代 `all_nodes()` 全量克隆
- 遍历引用统计，零克隆

## 后果 (Consequences)

### 正面影响
- **评分更新延迟**：从 60 秒降到 10 秒（增量重算）
- **评分重算性能**：从 O(n) 次锁+事务 → O(1) 次锁+事务（批量更新）
- **节点选择性能**：内存分配从 60000+ → 500
- **健康度计算**：零克隆（遍历引用统计）
- **冷热判断更智能**：多维度综合判定，高评分节点保底
- **代码可维护性**：智能逻辑集中在 intelligence 层，易于维护和优化

### 负面影响 / 代价
- **重构成本**：需要修改多个模块的调用方式
- **脏标记开销**：每次统计更新都要标记脏，有微小的性能开销（可忽略）
- **学习成本**：新开发者需要理解增量评分、脏标记、批量更新等概念

### 风险
- **脏标记遗漏**：如果某个统计更新路径忘记标记脏，会导致评分不更新
- **批量更新一致性**：批量更新过程中如果出错，可能导致部分评分未更新

### 缓解措施
- **代码审查**：所有统计更新路径必须经过审查，确保标记脏
- **全量兜底**：每 300 秒全量重算一次，即使有遗漏也能修正
- **单元测试**：为脏标记和批量更新编写单元测试
- **可观测性**：记录每轮增量重算的脏节点数量和重算耗时

## 替代方案 (Alternatives)

### 方案 A：保持全量重算
- 优点：简单，无需脏标记机制
- 缺点：性能差，60000 节点逐个更新，60 秒延迟
- 不选择的原因：性能问题严重，千万级节点时不可用

### 方案 B：实时评分（统计更新时立即重算）
- 优点：评分更新延迟最低
- 缺点：频繁的评分计算，CPU 开销大
- 不选择的原因：DHT 爬虫每秒收到很多响应，实时重算会占用大量 CPU

### 方案 C：冷热判断只看最后活跃时间（保持现状）
- 优点：简单
- 缺点：高评分节点可能被误降级，低评分节点占用内存
- 不选择的原因：多维度判定更智能，能更好地平衡内存和性能

## 验证标准 (Verification Criteria)

- [x] 评分更新延迟 < 10 秒（增量重算）
- [x] 增量重算耗时 < 100ms（通常 < 1000 个脏节点）
- [x] 节点选择内存分配 < 1000 个节点（Top 500 候选池）
- [x] 健康度计算零克隆（使用 stats()）

- [x] 127 个单元测试全部通过
- [x] PDC 启动后正常运行
