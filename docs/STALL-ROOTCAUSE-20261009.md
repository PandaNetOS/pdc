### S2 的关键设计决策（两处误报都是测试/实测抓出来的）

**误报① 纯队列判据不可用。** 初版判据2 写作「`in_flight==0` + 队列项距今 ≥120s」，
单元测试 `test_no_false_trigger_when_long_task_just_scheduled` **直接证伪**：

> 系统中存在 `interval` 达 300s 的长任务（bootstrap / range 反熵）。
> 正常空闲期与事故态在队列层面**完全同形** —— 都是「在飞 0 + 队列全在未来」，
> 纯队列判据无法区分，强行触发只会误杀正常空闲期并反复 abort。

**改用「在飞高水位」作区分信号**（`peak_in_flight`）：

| 状态 | 高水位 | 判定 |
|---|---|---|
| 正常空闲期 | 恒为 0（从未有在飞） | 不触发 |
| 事故态 | 曾有大量在飞后归零（本次事故 33 个泄漏槽位） | 触发 |

**误报② 预热期与停摆期同形（实测抓出）。** 首次部署后日志出现一次误触发：
进程启动后 ~2 分钟内任务正陆续注册，`in_flight==0` 属**正常**，
而高水位已因部分任务完成累积到 43 ⇒ 判据2 命中并误 abort 一次
（系统随后正常运行，属无害误报，但仍是误报）。

**改用「最近准入时刻」作豁免**（`last_admit_ms` + `STALL_STARTUP_GRACE_SECS=300s`）：
只要宽限期内还有任务被准入，就说明系统仍在正常调度，不判停摆。

> 两条误报共同印证一个原则：**停摆检测不能只看「当前状态」，
> 必须引入历史/过程信号**。当前状态（队列全在未来）同时对应
> 「正常空闲」「预热期」「真停摆」三种截然不同的情形。

### 压测脚本自身的 4 个 bug（压测前必须先验证脚本本身）

压测工具自己不可信等于没压测。首轮冒烟即暴露 4 处，全部修复：

| # | Bug | 现象 |
|---|---|---|
| 1 | `grep -c PAT \|\| echo 0` 无匹配时 grep 已输出 `0` 又追加 `0` | 得到 `0\n0`，`[` 报整数错 |
| 2 | 统计读**整份历史日志**，把上次事故的 08:15 泄漏算作本次失败 | FAIL（假的） |
| 3 | `BASE_LINES` 取**总行数**而 `grep -c` 数**匹配行数**，量纲不一致 | `泄漏=-12706`，并使 F4 误报 |
| 4 | **API 端口写错 6880**（实际 REST 挂在 `api_monitor_port=6886`） | 404 被当成无响应 |

> 第 4 条尤其关键：压测脚本「发现」的无响应其实是 404。
> **教训：压测必须先单独验证探活路径本身可用**，否则会把「探活方式错」
> 误判成「被测对象挂了」。

## 二、根本问题

**故障域与故障源被绑死。六 runtime 隔离只做到了「线程池分开」,没做到「资源分开」。**

三处共享资源收敛到同一瓶颈:

| 资源 | 现状 | 风险 |
|---|---|---|
| `Storage.conn: Arc<Mutex<Connection>>` | `db.rs` 38 处 + `io_scheduler.rs` 1 处 = **39 处直抢同一把锁** | 任何一处慢,全链路跟等 |
| `spawn_blocking` | **109 处**,`max_blocking_threads` 零配置 | 走 tokio 默认 512,与 worker 抢线程 |
| `api` runtime | 4 worker,Monitor 类全部挂上去 | 与 HTTP 共用,无隔离 |

**且写路径是双轨制**:`WriteQueue::send_sized` 与 `spawn_blocking(save_xxx)` 两条路
并存,两者抢同一把锁 —— 治本必须二选一收敛,不能各修一半。

## 三、为什么上一轮修复无效

`0da7730`(16:27)把 `db_entity_stats_refresh` 从 10 次抢锁降到 1 次,
是**在减少竞争,但没有消除结构**。39 处锁、109 处 blocking、双轨写路径全在。
它治了症状,没治病。

## 四、治本方案(四层)

### P0 ·唤醒保活兜底 —— 保证「发生了还能自愈」

> 这是四层里唯一**保证可恢复**的一层,其余三层是降低概率。

现状致命缺陷:watchdog(`task_scheduler.rs:1544` `reclaim_stale_slots`)是
**逐任务**判断超时回收,回收后只摘登记、**不重新驱动队列**。
⇒ 33 个槽位全回收后,`crawl=0/8` + 队列 21 恒定 **41 分钟**,无人恢复。

**改动**:

1. **全局停摆探测器**(新建,跑在 watchdog OS 线程)
   判据:`连续 N 个心跳(建议 N=4,即 2 分钟)满足`
   - `in_flight == 0`
   - `queue_len > 0` 且**队列最早到期项距今 > STALL_GAP_SECS**(建议 90s)
   - 且同期**全局任务完成计数无增长**(证明真的什么都没在跑)

   满足则判定停摆,立即:
   - 全量abort 所有 `in_flight` 登记项(已有 `abort_handle`,`0da7730` 已回填)
   - 把队列内所有项的 `scheduled_at` **重置为 now**(清队头/远期项)
   - 立即触发一轮 `process_queue`
   - 打 `ERROR` 级别告警 + 计数暴露到 `/io/status`

2. **队列延迟可观测**
   心跳增列两个字段:`队列最早到期=+Xs`、`队列最晚到期=+Ys`。
   现状只打 `队列待执行=21`,无法区分"21 个正常等待"与"21 个全被推到未来"——
   这是本次事故 41 分钟无人发现的直接原因。**这条比修复本身更重要。**

3. **回收即重驱动**
   `reclaim_stale_slots` 回收后,若 `in_flight` 归零而队列非空,主动触发一次准入。

---

### P1 · 写路径单一入口 —— 消除 39 处锁争用

目标:所有写操作收敛到 **一个串行写队列**,`self.conn.lock()` 在业务层归零。

1. **禁止裸抢锁**:给 `Storage` 加`#[cfg(debug_assertions)]` 断言守卫,
   开发期检测到async 上下文直接 `self.conn.lock()` 即 panic,防止新增。
2. **双轨合并**:全部写路径改走 `WriteQueue::submit`,`spawn_blocking(save_xxx)`
   这条轨删除(现存生产调用点已确认包了spawn_blocking,改造可控)。
3. **锁粒度分层**:按 `Metric` / `Node` / `Peer` / `Infohash` 拆写连接,
   参照读侧已有的 `read pool 24 + long-query pool 12 + permit 门限`成熟设计,
   写侧照抄同一套模式。**读侧已经治本了,写侧照抄即可,不需要新设计。**

> 参照物就在同一文件里:`read()` / `read_long()` / `read_long_priority()`
> 三级池+ permit 门限已跑通,写侧复用同一抽象。

---

### P2 · 资源额度显式化 —— 消除隐式共享

1. **显式 `max_blocking_threads`**(当前零配置,走默认 512)
   按 `runtime_worker_threads` 分级配额,DB 写 blocking 与爬虫 blocking 分池。
2. **Monitor 移出 api runtime**
   新增独立 `monitor` runtime(或至少独立 blocking 前缀),
   不与 HTTP 争抢 4 个 worker。`task_scheduler.rs:2305` 的映射需改。
3. **blocking 池耗尽可观测**
   `queued_count` / `max_blocking_threads` / `spawn_blocking` 等待时长进指标。

---

### P3 · 负载削减 —— 让堵点不再产生

1. **写入侧合并**:高频小事务(如 `update_infohash_score`)降频为批量。
2. **爬虫产出预算**:`paced 消费者` 已有 `预算=32/tick`,与IO 预算联动。
3. **零响应熔断续做**:逻辑已正确(`engine.rs:321-393`),
   但只挡链式采集一条路径 —— 扩展到主外发路径。

## 七、遗留待确认

1. ~~**队列 21 项为何全部 `scheduled_at` 落在未来**~~ —— **已排查,结论如下**:

   `apply_interval_jitter`(`task_scheduler.rs:994`)抖动系数为 `1 + ratio×uniform(-1,1)`,
   即区间 `[1-ratio, 1+ratio]`,**只可能小幅抖动,不会把 `scheduled_at` 推远**。

   ⇒ 推远机制不在间隔计算,而在于:`task_scheduler.rs:2440` 的
   「执行完成后 → `schedule_task(now + interval)` 重新入队」这段代码
   **位于 `fut` 内部**。任务体挂死 ⇒ 这段永不执行 ⇒ 队列项停留在
   *上一次*入队时给出的未来时间。

   **这恰好是 P0-1 判据的立论依据**:不是队列算错了,是没人再推进它。
   因此"队列最早/最晚到期距今"就是最直接的停摆信号,必须暴露出来。

2. **109 处 spawn_blocking 的分布画像** —— 需确认是否有本不该阻塞的操作混入。
3. **写路径双轨的调用点全景** —— `WriteQueue::send_sized` 与 `spawn_blocking`
   两条轨各有多少生产调用点,P1 合并前需完整清单。
