1. 背景与目标

1.1 为什么需要多 PDC 同步

PDC（节点发现 Agent）是 PandaNetOS 生态中的核心基础设施，负责 DHT 节点发现、BT Peer 索引、Tracker 池管理和超级 Tracker 服务。随着性能目标提升至超级 Tracker 10万 QPS、千万级数据规模，单实例架构面临以下挑战：

  • 单机性能极限：P3 优化清单已明确"多实例分片"作为未来方向，说明单机 10万 QPS 可能是物理极限
  • 地域覆盖需求：不同地域的 PDC 实例可以就近服务 BT 客户端，降低 announce 延迟
  • 高可用需求：单实例宕机导致整个节点发现服务中断，多实例可实现故障转移
  • 数据协同需求：各实例独立爬取的 DHT 节点和发现的 Peer 需要共享，避免重复劳动

1.2 同步目标

目标维度具体要求优先级
相互连接多 PDC 实例通过外网建立连接，支持 NAT 穿透，实例间可直接通信P0
同步数据四大 Repo（Node/Peer/Infohash/Tracker）数据在实例间同步，达到最终一致P0
协同工作写 QPS 可水平扩展，爬虫可协同，故障时自动转移P1
不破坏性能红线超级 Tracker 10万 QPS、<100μs 响应延迟、磁盘 IO <2MB/s、内存 <8GB红线
安全可控实例身份认证、传输加密、防伪造、防 Sybil 攻击P1

1.3 核心矛盾

同步的本质矛盾

1. 写密集 vs 同步带宽：PeerRepo 的 announce 是写密集型（目标 10万 QPS），如果每条 announce 都同步，带宽不可承受
2. 数据时效性 vs 一致性：DHT 节点和 BT Peer 高度动态，强一致代价极高且价值低
3. 单机极限 vs 水平扩展：多实例的核心诉求是水平扩展写性能，而非单纯数据共享
4. 控制面 vs 数据面：控制面信息量小需一致性，数据面信息量大允许最终一致

2.2 代码实证关键发现

重要代码实证修正

发现 1：dirty 机制只有 NodeRepo 有
PeerRepo/InfohashRepo/TrackerRepo 均无 dirty 标记。Gossip 方案若要复用 dirty，需先为 PeerRepo 补充 dirty 机制。

发现 2：PeerRepo 实际是单 RwLock，不是 64 分片
ShardedHashMap/DirtyShardedHashMap 已定义但未在 PeerRepo 中使用。超级 Tracker 的 SuperTrackerState.peers 使用 DashMap（内部分片），但 PeerRepo 缓存层是单 RwLock。10万 QPS 下 PeerRepo 的单 RwLock 是潜在瓶颈。

发现 3：UDP scrape 未实现
UDP scrape 返回 "scrape not implemented" 错误；HTTP /scrape 已实现，downloaded 恒为 0。

2.5 pnos-runtime 能力缺口

pnos-runtime 当前能力与定位差距大

pnos-runtime 当前是轻量级单实例组件注册中心 + 应用管理器，以下能力完全缺失：

  • 事件总线：pnos-sdk README 提到"事件订阅"，但 runtime 代码中无任何发布订阅实现
  • 数据同步/分发：完全不具备大规模数据同步、中继、分发能力

3.4 分片方案的致命伤

分片方案无法同时满足 <100μs 和数据归属

分片方案下 announce 到达非负责实例时必须转发，互联网 RTT 10~100ms，即使 LAN 也 0.1~1ms = 目标的 10 倍。五种路由模式分析：

  • 模式A 同步转发：延迟 1~50ms，直接破坏 <100μs ❌
  • 模式B 写本地+异步复制：announce 快了，但查询退化为全互联 fanout，失去分片意义 ⚠️
  • 模式C 客户端重定向：BEP 3 不标准支持重定向，UDP Tracker 无重定向机制 ❌
  • 模式D 入口层一致性哈希代理：需新增基础设施层，UDP 代理复杂度高 ⚠️
  • 模式E 协作式+部分响应：唯一保住 <100μs 的模式，但分片归属名存实亡 ✅（妥协）

结论：分片方案若要保持 <100μs，必须采用模式E，这实际上弱化了分片的归属意义——数据仍然分散在各实例，查询仍需跨实例合并。此时分片与 Gossip 的界限变得模糊，而 Gossip 的全量副本模型在查询完整性和 NAT 容错上更优。

4. 推荐方案详细设计

推荐方案：混合架构

控制面中心化（pnos-runtime）+ 数据面 Gossip P2P 同步 + CRDT 最终一致 + 三级 NAT 穿透 + Ed25519/Noise 安全

这是唯一能水平扩展写 QPS 的方案，与 PDC 现有架构（dirty/ShardedHashMap/事件总线/NatService）高度协同，带宽效率最高，与 P3"多实例分片"路线一致。

关键设计原则

  • 只同步"事实数据"（ip/port/id/last_seen），不同步"推导数据"（评分/统计/健康度）——推导数据各实例本地计算，从根本上减少冲突
  • 时效性字段本地化（last_active、ref_count 各实例独立维护），存在性/评分字段 gossip 化——将变更率从 10万/s 降至 ~4300/s
  • announce 热路径零侵入——Gossip 是异步后台任务，不进入 handle_udp_announce 同步调用链
  • 物理隔离——同步通道 6883 与 Tracker 通道 6880 完全隔离，加密开销不影响 Tracker 性能

4.2 数据分类同步策略

Repo同步层面同步策略同步频率不同步的字段
PeerRepo 数据面（P2P） Gossip 实时传播 + 仅热数据；LWW-Element-Set（基于 last_active） 实时（announce 触发，批量攒批 100条/1s） last_active（各实例本地维护）、connection_attempts（本地统计）
NodeRepo 数据面（P2P） 批量增量同步（复用 dirty 标记）；LWW-Register 属性 + G-Counter 统计 批量（5分钟间隔，dirty 节点批量） score（各实例独立评分）、query_count/success_count（本地统计）
InfohashRepo 数据面（P2P） Gossip 异步传播；PN-Counter（ref_count 精确计数）+ LWW-Register（source/score） 实时（随 peer 增减，增量 delta +1/-1） —（ref_count 用 PN-Counter 精确合并）
TrackerRepo 控制面（中心化） 实时同步（runtime 为源）；全量快照 LWW 合并 低频（变更触发 + 5min 心跳） —（数据量小，全量同步）
核心设计洞察

PDC 数据分为两类：事实数据（peer 的 ip/port、节点的 id/addr、infohash 的存在）和推导数据（评分、统计、健康度）。推导数据是各实例基于本地网络视角计算的，本就不应该同步。只同步事实数据后，冲突解决退化为简单的 LWW，不需要复杂的 CRDT（仅引用计数需要 PN-Counter）。

4.3 Gossip 同步协议设计

4.3.1 混合模式：Push Rumor Mongering + Pull Anti-Entropy

机制作用周期带宽
Push Rumor Mongering增量变更传播，低延迟500ms~1s低（仅传播变更）
Pull Anti-Entropy周期性对账修复，兜底一致性60s极低（摘要交换）

4.3.2 消息格式

GossipMessage {
    msg_id: u64,                  // 去重用
    origin_instance: [u8; 32],    // 发起实例 ID（Ed25519 公钥）
    repo_type: u8,                // 0=Node, 1=Peer, 2=Infohash, 3=Tracker
    op: u8,                       // 0=upsert, 1=delete
    hlc: Hlc,                     // 混合逻辑时钟（用于冲突解决）
    payload: bytes,               // 序列化的变更记录（bincode）
    signature: [u8; 64],          // Ed25519 签名
}

4.3.3 传播机制

  • fan-out：每个实例随机选择 f=4~8 个邻居传播
  • 去重：维护 seen_msgs（LRU，容量 100万），收到已处理的 msg_id 直接丢弃
  • TTL：消息带 TTL（3~5跳），防止无限传播
  • 攒批：announce 到达时不立即传播，在内存中攒批（100条或1秒），然后批量 gossip
  • 反熵：每60s随机选择1个邻居，交换 Merkle 树根哈希摘要，发现差异后 pull 修复

4.3.5 与 dirty 标记结合

  • NodeRepo：已有 dirty 机制（FxHashSet<SocketAddr>），直接作为增量同步数据源，每5分钟 take_dirty 批量发送
  • PeerRepo：需新增 dirty: RwLock<FxHashSet<(Infohash, SocketAddr)>>，在 add_peers_sync/remove_peer/update_score 时标记
  • InfohashRepo：利用 pending 缓冲区，register/unregister 时产生增量 delta
  • TrackerRepo：数据量小，全量快照同步，无需 dirty

4.4 一致性模型与 CRDT

4.4.1 为什么不需要强一致

PDC 没有任何数据需要 Raft/Paxos

1. PeerRepo：BT 协议本身就是最终一致的，peer 列表来自 DHT/Tracker/PEX 多源，多一条过期 peer 不影响下载
2. NodeRepo：DHT 节点池是候选池，多一个坏节点浪费一次探测，少一个好节点少一个候选
3. InfohashRepo：引用计数用 PN-Counter 精确合并，不需要强一致
4. TrackerRepo：数据量小，最终一致足够

4.4.2 四大 Repo 的 CRDT 映射

4.4.3 PN-Counter（Infohash ref_count）

struct PnCounterEntry {
    // per-instance counters: instance_id -> (positive, negative)
    counters: FxHashMap<InstanceId, (u32, u32)>,
    source: LwwRegister<String>,
    score: LwwRegister<f64>,
}

impl PnCounterEntry {
    fn value(&self) -> u32 {
        self.counters.values()
            .map(|(p, n)| p.saturating_sub(*n))
            .sum()
    }
    fn register(&mut self, instance: InstanceId) {
        self.counters.entry(instance).or_default().0 += 1;
    }
    fn unregister(&mut self, instance: InstanceId) {
        self.counters.entry(instance).or_default().1 += 1;
    }
    fn merge(&mut self, other: &Self) {
        for (id, (p, n)) in &other.counters {
            let local = self.counters.entry(*id).or_default();
            local.0 = local.0.max(*p);
            local.1 = local.1.max(*n);
        }
    }
}

同步时只传输增量 delta（{instance_id, infohash, +1/-1}），每条 ~40B，不全量传输 counters。

4.4.4 LWW-Element-Set（Peer 集合）

Peer 数据有 30 分钟 TTL，使用简化的 LWW-Element-Set 而非完整 OR-Set：

  • 不做显式 remove，只做 add（携带 last_active 时间戳）
  • 过期 peer 自动从集合中剔除（last_active > 30min）
  • 并发 add 同一 peer：取 max(last_active)，天然合并
  • 无需 tombstone，内存可控——任何冲突最多存在 30 分钟

4.4.5 HLC 混合逻辑时钟

struct Hlc {
    physical: u64,  // 毫秒级物理时钟
    counter: u32,   // 逻辑计数器
}

impl Hlc {
    fn increment(&mut self, now_ms: u64) {
        if now_ms > self.physical {
            self.physical = now_ms;
            self.counter = 0;
        } else {
            self.counter += 1;
        }
    }
    fn merge(&mut self, remote: &Hlc, now_ms: u64) {
        if remote.physical > self.physical {
            self.physical = remote.physical;
            self.counter = remote.counter + 1;
        } else if remote.physical == self.physical {
            self.counter = max(self.counter, remote.counter) + 1;
        } else {
            self.increment(now_ms);
        }
    }
}

HLC 替代裸时间戳解决 NTP 偏移问题：保证因果有序的事件不会被错误覆盖，且物理时钟分量仍接近真实时间可用于 TTL 判断。不用向量时钟——O(N) 空间在大规模下不可接受。

4.7 性能影响分析

4.7.1 对 10万 QPS / <100μs 的影响

announce 热路径零侵入

Gossip 是异步后台任务，不进入 handle_udp_announce 的同步调用链。announce 仍然纯本地内存操作，<100μs 目标不受影响。间接开销仅为 PeerRepo 增加 dirty 标记（每次 add_peer 多一次 HashSet insert，~100ns），可忽略。

4.7.2 安全机制 CPU 开销

安全机制计算开销对同步通道影响对 Tracker(6880) 影响
Noise XX 握手~200μs/连接每连接一次，长连接可忽略零（物理隔离）
ChaCha20-Poly1305~1-2μs/KB1000 msg/s × 200B = 0.2-0.4% CPU零
Ed25519 消息签名~20-50μs/条1000 msg/s = 2-5% CPU零
Ed25519 消息验证~50-100μs/条接收侧 5-10% CPU零
时间戳+序列号检查<1μs/条可忽略零

结论：安全机制对同步通道的 CPU 开销在 5-15% 范围内（主要是签名验证），对 10万 QPS 的 Tracker 服务通道零影响（物理隔离在 6883 端口）。如签名验证成为瓶颈，可批量签名（每10条签一次 batch signature）将验证开销降为 1/10。

4.7.3 内存开销

组件内存占用
Gossip outbox + seen_msgs 去重缓存~200-500 MB（千万级 key 的 dirty 集合）
同步发送缓冲区~10 MB
Merkle Tree（反熵摘要）~32 KB（1024 分片 × 32B）
PN-Counter per-instance countersN=10 时每 infohash 多 80B，可增量同步不全量传
HLC 状态每实例 12 字节，可忽略

4.7.4 磁盘 IO

无影响——同步数据来自内存（dirty/热数据），gossip 消息不需要持久化（丢失了靠反熵修复）。安全模块的私钥和 known_instances 文件仅在启动/连接时读写。

4.7.5 新实例冷启动

  • 全量数据大小：10M × 35B = 350 MB（紧凑二进制），gzip 后 ~100 MB
  • 从单实例拉取：100 MB ÷ 100 Mbps = 8s；从多实例并行拉取可加速到 2~3s
  • 冷启动期间需限流（如 50 MB/s），避免影响提供数据的实例的 announce
  • 新实例标记为 "warmup" 状态，不参与查询响应（或仅响应已有数据）

7.3 源报告核心结论索引

源报告核心结论
控制面报告pnos-runtime 能力缺口大（无事件总线/数据同步/持久化/集群）；主从写集中无法扩展 10万 QPS；混合架构唯一能水平扩展写 QPS，N=5 时集群总出口仅 16 Mbps；只同步事实数据，评分/统计各实例本地推导
P2P 报告dirty 机制只有 NodeRepo 有；PeerRepo 实际是单 RwLock 非 64 分片；Gossip 带宽每实例 ~2 Mbps 与实例数无关；分片方案跨实例转发破坏 <100μs，五种路由模式中只有模式 E 能保住延迟但分片归属名存实亡；UDP scrape 未实现
NAT/安全/一致性报告PDC NAT 模块已有 UPnP/NAT-PMP/PCP/STUN/UDP打洞/自定义中继/IPv6，缺 TURN/ICE/传输加密/实例身份；三级降级覆盖 95%+ 连接；Ed25519+Noise+消息签名+TOFU；四大 Repo 全部最终一致无需 Raft/Paxos；CRDT 映射：ref_count→PN-Counter，Peer→LWW-Element-Set，Node/Tracker→LWW-Register；HLC 替代裸时间戳；Peer 30min TTL 意味着冲突最多存在 30 分钟
